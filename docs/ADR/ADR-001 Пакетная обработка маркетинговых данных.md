# ADR-001: Пакетная обработка маркетинговых данных ^adr-001
## Контекст

Маркетинговому отделу требуется новое решение для расширенной пакетной обработки данных:
* Обрабатывать данные из разных источников
* Формировать отчеты

> [!IMPORTANT] Важно
> Текущая система обработки не справляется с нагрузкой и запрашиваемым функционалом

## Проблема

Выбрать и обосновать технологическое решение для пакетной обработки данных.

**Функциональность**:
 - позволять гибко формировать пайплайн
 - поддерживать встроенный мониторинг и оповещения

**Интеграции**:
 - с внешними API, BigQuery, Redshift, Kafka и Spark

**Инфраструктура**:
 - решение, применимое в облачной инфраструктуре.

## Условия

Источники

| Тип источника          | Данные                | Технология      |
| ---------------------- | --------------------- | --------------- |
| **Файловое хранилище** | Статусы доставок      | CSV / S3 / HDFS |
| **Реляционная БД**     | Заказы и платежи      | PostgreSQL      |
| **Стриминг**           | События модификации   | Apache Kafka    |
| **Внешние системы**    | Профили пользователей | REST API / CRM  |

Ожидаемая нагрузка
 - За один запуск пайплайна — около 1 млн. записей 

## Рассмотренные варианты
1. **Вариант А**: [Apache Airflow + Spark]
   1. Оркестрация - Apache Airflow
   1. Обработка данных - Apache Spark

1. **Вариант Б**: [Название]

## Решение
Выбрали вариант **Apache Airflow + Spark**

### Airflow позволяет гибко создавать пайплайн
- **[ADV] Преимущество**: Позволяет настраивать вариативные пути обработки, параметризовать запуски и версионировать логику 
	- [PROP] Свойства:
      - Использует программное описание пайплайнов (Pipeline as Code)
      - Есть ветвления и условия, чтобы направлять поток данных по разным путям (`BranchPythonOperator`)
      - Есть триггеры событий, по срабатыванию которых можно запускать шаги обработки (`Sensors`)
		
### Аргументация (Плюсы и Минусы)
*   **Плюсы**: 
    *   Отвечает функциональным требованиям
        *   Airflow Позволяет гибко создавать пайплайн
            *   Особенность
                *   Использует программное описание пайплайнов (Pipeline as Code)
                * Есть ветвления и условия, чтобы направлять поток данных по разным путям (`BranchPythonOperator`)
                * Есть триггеры событий, по срабатыванию которых можно запускать шаги обработки (`Sensors`)
              * Преимущества
                  * Можно настраивать вариативные пути обработки, параметризовать запуски и версионировать логику 
  
          * Airflow имеет встроенные средства мониторинга и оповещения
            * Особенность
              * есть богатый UI для отслеживания статусов задач
              * есть механизмы Callback-функций для отправки уведомлений в Slack, Telegram или Email
            * Преимущество
              * оперативное оповещение о сбое через привычные каналы
              * возможность мгновенно локализовать ошибку в конкретном узле пайплайна и перезапустить его, не тратя время на ручной поиск логов в серверах.
              
    * Отвечает требованиям по интеграции
      * **Особенность**
        * Airflow обладает одной из самых широких и зрелых экосистем операторов.
          * BigQuery & Redshift: Возможность переливать данные из локального хранилища в облачные DWH одной командой (`S3ToRedshiftOperator`)
          * Kafka: Возможность запускать задачи по событию или для микро-батчинга
          * Spark: Возможность делегирования тяжелых вычислений на кластер. (`SparkSubmitOperator` )
          * REST API / CRM: Возможность взаимодействия с любыми внешними сервисами. (универсальный оператор `HttpOperator`)
      * **Преимущество**
        * Готовые операторы интеграций максимально сократят срок разработки

    * Соответствует инфраструктуре
      * Airflow применим для облаков
        * Крупные провайдеры предлагают управляемые версии (Managed Airflow): MWAA (AWS), Cloud Composer (GCP), Managed Airflow (Azure).

    * Соответствует предполагаемой нагрузке
      * Spark обеспечит обработки в объеме 1 млн записей за запуск
        * Особенность
          * Выполняет реальную обработку (ETL) как изолированный компонент пайплайна
          * Масштабируется горизонтально
        * Преимущества
          * Гарантирует высокую производительность и надежность оркестратора без его перегрузки.

*    **Минусы**: 
* Сложность эксплуатации (Operational Overhead):
  * Особенность:
    *  Spark-кластер требует тонкой настройки (память исполнителей, количество ядер).
  * Риск: 
    * Неправильная конфигурация может привести к "зависанию" задач или неоправданно высоким счетам за облака.

* Порог входа (Learning Curve):
  * Особенность: 
    * Описание пайплайнов на Python требует навыков разработки (не просто SQL).
  * Ограничение: 
    * Потребуется время на обучение команды маркетинга или привлечение Data-инженеров для поддержки.

* Задержка запуска (Cold Start):
  * Особенность: 
    * Поднятие временного Spark-кластера в облаке (например, AWS EMR) может занимать 5–10 минут.
  * Ограничение:
    *  Решение не подходит для Real-time обработки, только для Batch (пакетной).

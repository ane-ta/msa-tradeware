# ADR-0001: Пакетная обработка маркетинговых данных

## Контекст

Маркетинговому отделу требуется новое решение для расширенной пакетной обработки данных:

- Обрабатывать данные из разных источников.
- Формировать отчеты.

> [!IMPORTANT]
> Текущая система обработки не справляется с нагрузкой и запрашиваемым функционалом.

## Проблема

Выбрать и обосновать технологическое решение для пакетной обработки данных, удовлетворяющий требованиям:

### Функциональные

1.  REQ-F-0001: Гибкое формирование пайплайнов

    Возможность динамически настраивать шаги обработки, ветвления и зависимости.

2.  REQ-F-0002: Мульти-интеграция

    Поддержка из коробки: API, BigQuery, Redshift, Kafka, Spark.

3.  REQ-F-0003: Встроенный мониторинг и уведомления

    Встроенное отслеживание статусов выполнения и уведомления при сбоях.

### Нефункциональные

1.  REQ-NF-0001: Cloud-Native архитектура

    Применимость в облаке (SaaS/PaaS) или контейнеризированной среде.

2.  REQ-NF-0002: Масштабируемость

    Стабильная обработка ~1 млн записей за один запуск (Batch).

3.  REQ-NF-0003: Совместимость данных

    Работа с CSV, S3, HDFS и реляционными БД (PostgreSQL).

    | Тип источника | Данные           | Технология            |
    |---------------|------------------|-----------------------|
    | **Файлы**     | Статусы доставок | `CSV` / `S3` / `HDFS` |
    | **БД**        | Заказы и платежи | `PostgreSQL`          |
    | **Стриминг**  | События          | `Apache Kafka`        |
    | **Внешние**   | Профили          | `REST API` / `CRM`    |

## Решение

**Apache Airflow + Apache Spark**

## Аргументация

### ➕ Airflow позволяет гибко создавать пайплайн

- **Можно:**
  - настраивать вариативные пути обработки,
  - параметризовать запуски
  - и версионировать логику.
- **Так как:**
  - Пайплайн конфигурируется через код (Pipeline as Code)
  - `BranchPythonOperator`
    - Есть операторы ветвления и условия, чтобы направлять поток данных по разным путям
  - Операторы-триггеры `Sensors`
    - Есть триггеры событий, по срабатыванию которых можно запускать шаги обработки
  - Параметры запуска `retries` и `retry_delay`
    - позволяют автоматически перезапускать упавшие задачи.
- **Реализует:**
  - [id:req-f-0001](id:req-f-0001)

### ➕ Airflow имеет встроенные средства мониторинга и оповещения

- **Можно:**
  - настроить оперативное оповещение о сбое через привычные каналы
  - мгновенно локализовать ошибку в конкретном узле пайплайна и перезапустить его, не тратя время на ручной поиск логов в серверах.
- **Так как:**
  - есть богатый UI с отслеживанием статусов задач
  - `email_on_failure` и `email_on_retry`
    - есть механизмы отправки уведомлений в Slack, Telegram или Email
- **Реализует:**
  - [id:req-f-0003](id:req-f-0003)

### ➕ Airflow позволяет быстро реализовать необходимые интеграции

- **Можно:**
  - Использовать готовые операторы интеграций, чтобы максимально сократить срок разработки
- **Так как:**
  - чтобы переливать данные из локального хранилища в облачные DWH одной командой
    - для BigQuery `BigQueryInsertJobOperator`
    - для Redshift `S3ToRedshiftOperator`
  - чтобы заходить в базу и выполнять запросы
    - для PostgreSQL `PostgresOperator`
    - для BigQuery `BigQueryOperator`
  - Kafka: запускать задачи по событию или для микро-батчинга
  - `SparkSubmitOperator` для Spark:
    - чтобы делегировать тяжелые вычисления на кластер.
  - `SimpleHttpOperator` для REST API / CRM:
    - чтобы взаимодействовать с любыми внешними сервисами.
- **Реализует**:
  - [id:req-f-0002](id:req-f-0002)

### ➕ Подходит для облачной инфраструктуры

- **Можно:**
  - Локально запускать через Docker Compose.
  - Разворачивать в облаке.
  - Передать обслуживание облачному провайдеру
  - Продолжить выполнение прерванного пайплайна после перезапуска
- **Так как:**
  - Имеет микросервисную архитектуру
  - Сохраняет промежуточное состояние выполнения пайплайнов
  - `KubernetesExecutor` запускает каждую задачу в отдельном изолированном поде по необходимости
  - Крупные провайдеры предлагают управляемые версии Airflow:
    - MWAA (AWS),
    - Cloud Composer (GCP),
    - Managed Airflow (Azure).
- **Реализует**:
  - [id:req-nf-0001](id:req-nf-0001)

### ➕ Решение соответствует предполагаемой нагрузке

- **Можно:** Гарантировать высокую производительность и надежность пайплайна при росте нагрузки.
- **Так как:**
  - Spark обеспечит обработки в объеме 1 млн записей за запуск
    - Выполняет реальную обработку (ETL) как изолированный компонент пайплайна
    - Масштабируется горизонтально
- **Реализует**:
  - [id:req-nf-0002](id:req-nf-0002)

- **Так как:**
  - Описание пайплайнов требует навыков разработки на Python (не просто SQL).

- **Так как:**
  - Spark-кластер требует тонкой настройки (память исполнителей, количество ядер)

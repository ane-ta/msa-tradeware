* ADR-0001: Архитектура модуля пакетной обработки данных
  :PROPERTIES:
  :ID:       adr-0001
  :REFERS_TO_REQ: 
  :STATUS:   PROPOSED
  :DATE:     2026-03-17
  :END:

** Контекст
Каждое утро в 6:00 нужно сгенерировать кастомные CSV/XLS-прайс-листы для B2B-клиентов на основе текущих данных в БД. 

Инфраструктура: микросервисы в облаке

** Проблема
Предложить архитекуру модуля пакетной обработки, удовлетворяющую требованиям:
- Функциональность:
  - Запуск по расписанию (каждый день в 6:00),
  - Исходные данные из SQL БД прода.
  - Необходимо связать данные из 4 таблиц и выгрузить их в CSV-файл. 
  - дополнительной логики по обработке данных не требуется. 

- Профиль нагрузки:
  - запуск 1 раз в сутки
  - 5 000–10 000 строк за запуск.
      - products ~ 5 000–10 000 строк;
      - categories ~ 50–200 строк;
      - clients ~ 100–500 строк;
      - client_prices ~ 10 000–20 000 строк.

- Надежность:
  - Гарантировать результат к началу рабочего дня

- Интеграция:
  - Не должен перегружать БД прода

- Тенденции:
  - По нагрузке: O(количества продуктов * кол-во клиентов) 

** Рассмотренные решения
*** ✅ Решение 1 (Python Script + K8s CronJob)
  :PROPERTIES:
  :TYPE: ADR_SOLUTION_ACCEPTED
  :END:
- *Суть:*
  - Легковесный контейнер, запускаемый планировщиком Kubernetes по расписанию.
- *Выбрано:*
  - Идеально покрывает требования без оверхеда по ресурсам и сложности.
  - Минимальное время доставки

*** ❌ Решение 2 (Spring Batch + K8s CronJob)
  :PROPERTIES:
  :TYPE: ADR_SOLUTION_REJECTED
  :END:
- *Суть:*
  - Реализация типичной ETL-логики на Java/Spring
- *Отклонено:*
  - Неэффективен по ресурсам
    - Слишком тяжелый для текущих требований. Высокий порог входа и временные затраты на разработку типовых ETL-компонентов там, где достаточно одного SQL-запроса».

*** ❌ Решение 3 (Airflow)
  :PROPERTIES:
  :TYPE: ADR_SOLUTION_REJECTED
  :END:
- *Суть:*
  - Использование полноценной платформы для управления конвейерами рабочих процессов (DAG).
- *Отклонено:*
    - Избыточен:
      - Стоимость владения и сложность настройки перевешивают выгоду от наличия UI и графа зависимостей, которые в случае запуска изолированной задачи не востребованы.

** Решение
Выбрано Решение 1: Python Script + K8s CronJob

** Аргументация
*** ➕ Отвечает всем функциональным требованиям
  :PROPERTIES:
  :TYPE: ADR_ADVANTAGE
  :REFERS_TO_ASPECT: Функциональность
  :REFERS_TO_REQ: 
  :END:
- Запуск по расписанию - K8s CronJob
- Csv файл из результатов запроса к бд - скрипт на Python

*** ➕ Адекватен планируемой нагрузке
  :PROPERTIES:
  :TYPE: ADR_ADVANTAGE
  :REFERS_TO_ASPECT: Производительность
  :REFERS_TO_REQ: 
  :END:
- *Можно:*
  - Обработать все данные единым запросом без разбиения на чанки. 
- *Так как:*
  - Нагрузка на БД прода мизерная: Запрос в 10 000 строк и 4 JOIN-ов для проиндексированных таблиц PostgreSQL займет 100-500 млсек.
  - Нагрузка на оперативную память мизерная: Результат в текстовом виде займет примерно 2-5MB.

*** ➕ Обеспечивает необходимую надежность
  :PROPERTIES:
  :TYPE: ADR_ADVANTAGE
  :REFERS_TO_ASPECT: Надежность
  :REFERS_TO_REQ: 
  :END:
- *Можно:*
  - Гарантировать результат к началу рабочего дня.
- *Так как:*
  - В K8s CronJob есть параметры:
    - backoffLimit, чтобы дать несколько попыток на выполнение скрипта.
    - activeDeadlineSeconds, чтобы Job не зависла.
  - В Grafana позволяет настроить алерт на отсутствие свежего файла к 06:15.
  - Логи из K8s собираются автоматически, если в кластере настроен сборщик (Promtail или Fluentd). Скрипт может отчитаться о возникших проблемах в stdout.
  - В Kubernetes можно смотреть события самого CronJob: ~kubectl get events~

*** ➕ Экономически эффективен
  :PROPERTIES:
  :TYPE: ADR_ADVANTAGE
  :REFERS_TO_ASPECT: Стоимость
  :REFERS_TO_REQ: 
  :END:
- *Можно:*
  - Использовать ресурсы облака только в момент выполнения задачи (2-5мин в сутки).
- *Так как:*
  - Нет необходимости держать постоянно запущенный инстанс или дополнительную инфраструктуру.

*** ➕ Самый быстрый time-to-market
  :PROPERTIES:
  :TYPE: ADR_ADVANTAGE
  :REFERS_TO_ASPECT: Стоимость
  :REFERS_TO_REQ: 
  :END:
- *Можно:*
  - Написать за часы, а не дни.
- *Так как:*
  - Не нужно настраивать сложных пайплайнов или мета-таблиц.

** Ограничения и риски
*** ⚙️ Базовая наблюдаемость
  :PROPERTIES:
  :TYPE: ADR_CONSTRAINT
  :REFERS_TO_ASPECT: Наблюдаемость
  :REFERS_TO_REQ: 
  :END:
- *Нужно:*
  - Отслеживать успешность выполнения через внешние системы (Prometheus/Grafana).
- *Так как:*
  - Нет своего UI

*** ⚠️ Риск роста нагрузки на основную БД прода
  :PROPERTIES:
  :TYPE: ADR_RISK
  :REFERS_TO_ASPECT: Производительность
  :REFERS_TO_REQ: 
  :END:
  - *Может:*
    - Замедлиться работа основного магазина при увеличении объема выгружаемых строк до миллионов.
  - *Так как:*
    - Запрос к базе потяжелеет.
  - *Решение*
    - Использовать Read-Only реплики БД и уровня изоляции Read Committed, чтобы гарантированно не блокировать транзакции записи в основном магазине».

*** ⚠️ Риск снижения производительности и надежности
  :PROPERTIES:
  :TYPE: ADR_RISK
  :REFERS_TO_ASPECT: Производительность Надежность
  :REFERS_TO_REQ: 
  :END:
  - *Может:*
    - При увеличении количества продуктов и клиентов может стать нецелесообразным обрабатывать данные одним запросом.
  - *Так как:*
    - При перезапуске скрипта обработка данных будет запускаться заново.
  - *Решение*
    - Мигрировать на Spring Batch и использовать чанки.

*** ⚠️ Риск усложнения бизнес-логики
  :PROPERTIES:
  :TYPE: ADR_RISK
  :REFERS_TO_ASPECT: Функциональность
  :REFERS_TO_REQ: 
  :END:
- *Может:*
  - Потребоваться сложная трансформация данных, которую будет больно реализовывать в python.
- *Так как:*
  - Бизнесу может потребоваться развитие в этом направлении.
- *Решение*:
  - Мигрировать логику на Spring Batch, сохранив запуск через K8sCronJob.

*** ⚠️ Риск увеличения количества задач пакетной обработки  
  :PROPERTIES:
  :TYPE: ADR_RISK
  :REFERS_TO_ASPECT: Администрирование
  :REFERS_TO_REQ: 
  :END:
- *Может:*
  - Оказаться тяжело управлять десятком подобных CronJob-скриптов.
- *Так как:*
  - Скрипты независимы и разрозненны.
- *Решение*
  - Внедрить полноценный оркестратор (например, Apache Airflow), чтобы централизованно управлять зависимостями и расписанием всех цепочек процессов.

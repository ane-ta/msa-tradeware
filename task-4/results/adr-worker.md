# ADR-0002: Выбрать технологию для реализации этапа обработки данных ETL-пайплайна

## Контекст

Для проектирования ETL-пайплайна из [id:adr-0001](id:adr-0001) необходимо выбрать технологию реализации процесса обработки.

## Проблема

Выбрать технологию, наиболее близко соответствующую типу задачи:

- Тип процесса:
  - Классический ETL-пайплайн без сложного ветвления процесса
- Масштаб:
  - Средний
    - Объем данных (до 400 000 строк) уже не позволяет обрабатывать файл целиком в оперативной памяти (риск OutOfMemory), но еще не требует распределенных вычислений.
- Сложность трансформации:
  - Высокая
    - Процесс требует обогащения данных из внешних справочников БД и построчной бизнес-валидации перед записью.
- Критичность состояния:
  - Высокая
    - Процесс длительный (до 15-30 минут), поэтому важна возможность продолжения с места сбоя для соблюдения регламентов смены.
- Режим работы:
  - Фоновая асинхронная обработка с уведомлением пользователя о результате.

## Решение

Выбран Spring Batch

## Аргументация

### ➕ Обеспечивает производительность для уровня нагрузки

- **Можно:**
  - Обеспечить высокую пропускную способность и минимизировать нагрузку на БД.
- **Так как:**
  - Есть механизм обработки данных пакетами Chunk-processing

### ➕ Restartability (Перезапускаемость) Позволяет минимизировать последствия долговременных сбоев

- **Можно:**
  - Продолжить прерванную задачу обработки с места сбоя.
- **Так как:**
  - Встроенный JobRepository хранит чекпоинты уже обработанных пакетов.

### ➕ Выносится в отдельный микросервис

- **Можно:**
  - разгрузить монолит от обработки отчетов и защитить его производительность
  - легко масштабировать ресурсы под пиковые нагрузки
  - развернуть в облаке
- **Так как:**
  - Spring Batch можно вынести в отдельный воркер и контейнизировать в докер

### ➕ Соответствует текущим и будущим характеристикам пайплайна

- **Можно:**
  - просто реализовывать сложную логику валидации и обогащения данных
  - просто интегрировать разные источники данных для обогащения
  - просто менять этапы обработки
- **Так как:**
  - Имеет встроенные инструменты для этих задач
  - Использует модульный подход для описания шагов (Reader, Processor, Writer)

### ➕ Устойчив к кратковременным сбоям и единичным ошибка данных

- **Можно:**
  - обработать кратковременные ошибки связи с источниками данных
  - пропустить единичный ошибки в данных
- **Так как:**
  - Есть встроенные механизмы Retry для шагов обработки и чанков
  - Есть встроенные механизмы пропуска проблемных строк

## Ограничения и риски

### ⚙️ Необходимо реализовать инструмент для мониторинга и управления запущенными пайплайнами

- **Нужно:**
  - Control Plane: Реализовать и интегрировать интерфейс управления задачами существующих обработок.
- **Так как:**
  - Нет встроенного UI инструмента
- **Решение:**
  - Использовать Spring Boot Actuator для экспорта метрик (кол-во строк, статус) в существующую систему мониторинга.
  - Реализовать в Воркере легковесный REST API (эндпоинт /jobs/restart/{id}), который вызывает метод JobOperator.restart()
  - Добавить кнопку «Перезапустить» в существующую панель управления ERP, которая будет отправлять HTTP-запрос к Воркеру.

### ⚙️ Необходимо обеспечить обратную связь от воркера

- **Нужно:**
  - Пробросить информацию о статусе и событиях обработки пользователю, администратору и монолиту как хранителю истории.
- **Так как:**
  - Воркер - самостоятельный изолированный процесс.
- **Решение:**
  - JobExecutionListener или SkipListener в Spring Batch для определения момента отправки обратной связи
  - HTTP POST (Webhook) для отправки обратной связи
  - REST API контракт монолита для реакции на обратную связь.

### ⚙️ Операционные затраты

- **Нужно:**
  - Разворачивать и поддерживать отдельную базу метаданных для JobRepository
- **Так как:**
  - Это техническое требование фреймворка для обеспечения атомарности и сохранения чекпоинтов (Restartability)
- **Риск**:
  - Усложнение инфраструктуры и необходимость управления схемами в двух разных БД.

### ⚙️ Компетенции команды по фреймворку

- **Нужно:**
  - Понимать жизненный цикл Job/Step
  - Уметь настраивать политики пропусков и повторов
  - Уметь использовать разные источники для загрузки
- **Риск**
  - Неправильная конфигурация может привести к потере невалидных строк без должного логирования или к снижению производительности при неверном размере чанка.

### ⚙️ Временная несогласованность

- **Нужно:**
  - Учитывать, что в базе будет находиться частично актуальная информация по остаткам во время обработки отчета
- **Так как:**
  - Данные фиксируются в БД пачками (Chunks) в течение 15–20 минут, а не одной транзакцией на весь файл.
- **Решение:**
  - Показывать статус «В процессе» в интерфейсе ERP и использование уведомлений для сотрудников.

| ****Apache Airflow**** | Лидер в области оркестрации данных с богатой экосистемой операторов. | **Слабая работа с данными:** <br>Плохо подходит для трансформации каждой из 400к строк внутри себя и обеспечении транзакционности чанков. <br>Требует внедрения Python в Java-стек. |
| ****Apache Spark**** | Промышленный стандарт для параллельной обработки огромных массивов данных (Big Data). | **Overkill (Избыточность):** <br>Требует развертывания кластера, что неоправданно дорого и сложно для текущего масштаба (400к строк). |
| ****Jakarta Batch (JSR 352)**** | Официальный стандарт Java EE для пакетной обработки (реализован в WildFly через JBeret). | **Ограниченность экосистемы:** <br>Сеньше готовых коннекторов (Readers/Writers)<br>Слабее поддержка сообщества, что увеличивает время разработки. |
| ****Custom Java Logic (for-each)**** | Ручная реализация логики | **Сложная и трудозатратная разработка:** <br>Ручная реализация механизмов **Restartability** (чекпоинтов) и пакетной записи транзакциями крайне трудозатратна и подвержена ошибкам. |

Spring Batch выбран как «золотая середина»:

- Он обладает мощностью Spark для пакетной обработки,
- При этом остается легковесным Java-приложением
- Идеально вписывается в текущий стек
- Закрывает требования по Restartability и Throughput без лишних затрат на инфраструктуру и разработку.

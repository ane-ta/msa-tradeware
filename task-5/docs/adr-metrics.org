* ADR-002: Состав метрик для мониторинга ETL-процессов
  :PROPERTIES:
  :ID:       adr-002
  :REFERS_TO_REQ: 
  :STATUS:   PROPOSED
  :DATE:     2026-03-29
  :END:

** Контекст
Аархитектура на базе OpenTelemetry позволяет собирать неограниченное количество данных. 
Однако избыток метрик ведет к «информационному шуму» и росту затрат на хранение (Cardinality). 

** Проблема
Необходимо определить минимальный и достаточный набор метрик для контроля складских отчетов.

** Решение
Установить стандарт на три группы метрик с обязательной разметкой job_id и trace_id:
- Группа А: Бизнес-метрики (Целостность данных)
    - batch_records_read_total: количество строк, успешно считанных из CSV.
    - batch_records_written_total: количество записей, успешно записанных в БД.
    - batch_records_skipped_total: количество строк, отфильтрованных из-за ошибок валидации.
    - Критерий успеха: read == written + skipped.

- Группа Б: Производительность (SLA)
    - batch_job_duration_seconds: общее время выполнения джобы.
    - batch_step_execution_seconds: время выполнения отдельных этапов (валидация, обогащение).
    - batch_item_processing_rate: скорость обработки записей (items/sec).

- Группа В: Стабильность (Health)
    - batch_job_status: перечислимая метрика (0 — Success, 1 — Failed, 2 — Abandoned).
    - jvm_memory_used_bytes: загрузка Heap-памяти во время обработки тяжелых файлов.
    - gcs_connection_errors_total: количество сбоев при обращении к облачному хранилищу.

- Инфраструктурные:
    - Доступность Google Cloud Storage (ошибки подключения).

** Ограничения и риски
*** ⚠️ Риск высокой кардинальности
  :PROPERTIES:
  :TYPE: ADR_RISK
  :REFERS_TO_ASPECT: Надежность
  :REFERS_TO_REQ: 
  :END:
- *Когда:*
  - Если в качестве меток (labels) к метрикам добавить уникальные значения, например file_name или user_id.когда может произойти...
- *Может:*
  - Привести к резкому росту потребления памяти Prometheus и замедлению построения графиков.
- *Решение:*
  - Запретить использование динамических строк в метках. Для детального анализа конкретного файла использовать trace_id в логах, а не в метриках.

*** ⚠️ Риск потери метрик при фатальном сбое
  :PROPERTIES:
  :TYPE: ADR_RISK
  :REFERS_TO_ASPECT: Надежность
  :REFERS_TO_REQ: 
  :END:
- *Когда:*
  - Приложение «падает» с OutOfMemory до того, как успевает отправить (push) метрику завершения.
- *Может:*
  - Система мониторинга не получит статус Failed, джоба просто «исчезнет» с радаров.
- *Решение:*
  - Настроить алерт «Absence of data» (отсутствие данных) — если джоба началась, но не завершилась в течение ожидаемого времени SLA.

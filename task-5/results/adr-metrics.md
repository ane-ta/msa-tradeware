# ADR-002: Состав метрик для мониторинга ETL-процессов

## Контекст

Аархитектура на базе OpenTelemetry позволяет собирать неограниченное количество данных. Однако избыток метрик ведет к «информационному шуму» и росту затрат на хранение (Cardinality).

## Проблема

Необходимо определить минимальный и достаточный набор метрик для контроля складских отчетов.

## Решение

Установить стандарт на три группы метрик с обязательной разметкой job<sub>id</sub> и trace<sub>id</sub>:

- Группа А: Бизнес-метрики (Целостность данных)
  - batch<sub>records</sub>\_read<sub>total</sub>: количество строк, успешно считанных из CSV.
  - batch<sub>records</sub>\_written<sub>total</sub>: количество записей, успешно записанных в БД.
  - batch<sub>records</sub>\_skipped<sub>total</sub>: количество строк, отфильтрованных из-за ошибок валидации.
  - Критерий успеха: read == written + skipped.
- Группа Б: Производительность (SLA)
  - batch<sub>job</sub>\_duration<sub>seconds</sub>: общее время выполнения джобы.
  - batch<sub>step</sub>\_execution<sub>seconds</sub>: время выполнения отдельных этапов (валидация, обогащение).
  - batch<sub>item</sub>\_processing<sub>rate</sub>: скорость обработки записей (items/sec).
- Группа В: Стабильность (Health)
  - batch<sub>job</sub>\_status: перечислимая метрика (0 — Success, 1 — Failed, 2 — Abandoned).
  - jvm<sub>memory</sub>\_used<sub>bytes</sub>: загрузка Heap-памяти во время обработки тяжелых файлов.
  - gcs<sub>connection</sub>\_errors<sub>total</sub>: количество сбоев при обращении к облачному хранилищу.
- Инфраструктурные:
  - Доступность Google Cloud Storage (ошибки подключения).

## Аргументация

### ➕ Позволяет контролировать целосность

- **Можно:**
  - обнаружить «тихую» потерю данных, если часть строк не дошла до базы.
- **Так как:**
  - Есть сравнение read и written

### ➕ Обеспечивает оперативное реагирование

- **Можно:**
  - отправить немедленный алерт в Telegram/Email на внештатные ситуации
- **Так как:**
  - есть метрика batch<sub>job</sub>\_status со значением 1 (Failed)

### ➕ Помогает оптимизировать ресурсы при обработке

- **Можно:**
  - выявить утечки памяти при обработке сверхбольших CSV-файлов еще до падения системы
- **Так как:**
  - есть мониторинг jvm<sub>memory</sub>

### ➕ Позволит ввести SLA на ETL пайплайны

- **Можно:**
  - Выявлять узкие места при обработке данных
- **Так как:**
  - Есть метрики длительности шагов

## Ограничения и риски

### ⚠️ Риск высокой кардинальности

- **Когда:**
  - Если в качестве меток (labels) к метрикам добавить уникальные значения, например file<sub>name</sub> или user<sub>id</sub>.когда может произойти…
- **Может:**
  - Привести к резкому росту потребления памяти Prometheus и замедлению построения графиков.
- **Решение:**
  - Запретить использование динамических строк в метках. Для детального анализа конкретного файла использовать trace<sub>id</sub> в логах, а не в метриках.

### ⚠️ Риск потери метрик при фатальном сбое

- **Когда:**
  - Приложение «падает» с OutOfMemory до того, как успевает отправить (push) метрику завершения.
- **Может:**
  - Система мониторинга не получит статус Failed, джоба просто «исчезнет» с радаров.
- **Решение:**
  - Настроить алерт «Absence of data» (отсутствие данных) — если джоба началась, но не завершилась в течение ожидаемого времени SLA.

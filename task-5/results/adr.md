# ADR-001: Централизованная система мониторинга и логирования

## Контекст

- Текущая ситуация:
  - В случае ошибок трудно
    - отследить причину её возникновения
  - Отсутствуют средства мониторинга
  - Есть только
    - стандартный мониторинг ресурсов VM и WildFly монолита.
    - логи в файл
- Текущая архитектура:
  - монолит + БД
    - складские остатки товаров и перемешения товаров
      - формирует об этом отчеты
      - предоставляет пользовательский интерфейс
        - сотрудник склада в конце рабочей смены загружает отчёт об:
          - остатках
          - и перемещениях.
  - сервис учета хранения и логистических операций
    - формирует отчёты о движении товаров и выгружает их в CSV по факту перемещения товаров.
  - фронтенд приложение
    - отображение
      - текущих остатков товаров,
      - истории перемещений
      - и аналитики.
  - ETL-пайплайны для обработки отчетов об остатках и перемещениях на складах
  - хостинг файлов с отчетами - в облаке - Google Cloud Storage

Запросы бизнеса:

- Внедрить систему централизованного сбора логов и метрик, которая:
  - будет сочетаться с микросервисной архитектурой.
  - снизит MTTR (Mean Time To Repair) - времени на поиск и исправление ошибок в отчетах.
  - позволит контролировать целостность данных: что все остатки со склада загружены полностью и вовремя.

## Технический анализ

1.  **Отсутствие бизнес-контекста**:
    - мониторятся только метрики инфраструктуры и ресурсов в монолите
2.  **Разрозненность**: Невозможно связать всю инфомацию воедино в момент аварии.
    - Логи лежат в текстовом файле
    - метрики CPU — в Zabbix,
    - ошибки БД — в консоли WildFly.
3.  **Нет Trace ID**:
    - По ошибке в WildFly непонятно, к какому конкретно процесу или пользователю она относится.

## Проблема

Спроектировать систему централизованного сбора логов и метрик для архитектуры:

1.  **Сетевая топология и доступность**
    - Сервисы в облачной подсети.
2.  **Жизненный цикл**
    - Монолит - постоянная доступность
    - ETL пайплайны - периодическая доступность
3.  **Степень связности**
    - Единая картина
4.  **Модель индексации и поиска**
    - Достаточно искать по метаданным (ID сервиса, TraceID, дата)
5.  **Тяжесть мониторинга**
    - Количество микросервисов - возле десятка
6.  **Изолированные сегменты**
    - Нет

### Функциональные требования

1.  REQ-F-001: Сводить логи и метрики в одну картину

    Возможность перехода от графика ошибки в метриках к конкретным строкам лога по метке времени и ID операции (Trace ID)

2.  REQ-F-002: В случае ошибок предоставлять информацию, по которой легко отследить причину её возникновения

### Нефункциональные требования

1.  REQ-NF-001: Сочетается с микросервисной и облачной архитектурой

## Рассмотренные решения

### ✅ OTel(Agent) + Prometheus(Metrics) + Loki(logs) + Grafana (UI)

- **Суть:**
  - Универсальный конвейер независимый от вендора.
- **Выбрано:**
  - Гарантированная корреляция между логами и метриками
  - Минимальное число архитектурных элементов
  - Сохраняет максимальную гибкость в переходе на другие технологии обеспечения наблюдаемости.

### ❌ ELK Stack (Filebeat, Elasticsearch, Logstash, Kibana)

- **Суть:**
  - Тяжелая аналитика и полнотекстовой поиск
- **Отклонено:**
  - Слишком тяжелый для задачи. Полнотекстовый поиск не является критическим требованием, а ресурсы на его поддержку в облаке высоки.

### ❌ Чистый Prometheus + Grafana PLG Stack (Promtail, Loki, Grafana)

- **Суть:**
  - Вендорские экосистемы - использование узкоспециализированных инструментов, которые идеально работают друг с другом, но требуют жесткой привязки к конкретному формату данных (labels) и протоколам (Push/Pull).
- **Отклонено:**
  - Отсутствие гибкости. Прямая связка компонентов делает систему хрупкой. Любая смена БД потребует перенастройки всех агентов. Нет встроенной поддержки распределенной трассировки «из коробки» на уровне единого протокола.

## Решение

Micrometer SDK + OTel(Agent) + Prometheus(Metrics) + Loki(logs) + Grafana (UI)

- Micrometer - Java SDK для генерации метрик и проброса TraceID
- OTel(Agent) - Собирает с сервисов метрики и логи
  - long-running сервисы - по модели Pull
  - jobs - по модели Push
- Prometheus - обрабатывает поток метрик
- Loki - обрабатывает поток логов
- Grafana - визуализирует метрики и логи по TraceId, бросает алерты

## Аргументация

### ➕ Гарантирует сквозную корреляцию логов и метрик

- **Можно:**
  - Мгновенно связывать аномалии на графиках с конкретными событиями в логах.
- **Так как:**
  - Использование единого стандарта OTLP и библиотеки Micrometer Tracing обеспечивает автоматическую проброску TraceID во все типы сигналов.
  - В Grafana это реализует «бесшовный» переход: от всплеска ошибок на графике к детальному логу обработки конкретной транзакции.

### ➕ Лаконичен по набору компонентов

- **Можно:**
  - Снизить накладные расходы на ресурсы VM и упростить эксплуатацию системы.
- **Так как:**
  - Используется единый OTel Collector вместо нескольких узкоспециализированных агентов
    - Filebeat для логов,
    - JMX-exporter для метрик,
    - Jaeger для трейсов,
    - Prometheus push - для сбора метрик по модели push.

### ➕ Экономически эффективен

- **Можно:**
  - минимизировать затраты на хранение (Storage) и вычислительные ресурсы (CPU/RAM)
- **Так как:**
  - Loki индексирует только метаданные (labels).
  - Это позволяет хранить глубокую историю логов в дешевом облачном хранилище (GCS) без деградации производительности поиска.

### ➕ Обеспечивает архитектурную гибкость при переходе на Cloud-Native

- **Можно:**
  - Заменять элементы решения без изменения продуктовых сервисов, в том числе переходить на Managed Service.
- **Так как:**
  - OpenTelemetry выступает абстрактным слоем между кодом и системами хранения. Это избавляет от «vendor lock-in».

### ➕ Обеспечивает гибкое масштабирование

- **Можно:**
  - Гарантировать надежность системы наблюдения под нагрузкой
- **Так как:**
  - OTel:
    - горизонтально масштабируется
    - имеет встроенные механизмы, которые спасают систему мониторинга от «смерти»:
      - Memory Limiter: Если памяти становится мало, он начинает отбрасывать данные или притормаживать прием, чтобы не упасть самому и не уронить сервер.
      - Batching: Он группирует мелкие метрики в большие пакеты перед отправкой. Это радикально снижает количество сетевых запросов к Prometheus и Loki.
    - позволяет поднять
      - Gateway (Cluster): Мощный кластер коллекторов в отдельной подсети. Они занимаются тяжелой работой: парсингом JSON, обогащением метаданными и записью в Loki/Prometheus.

## Ограничения и риски

### ⚙️ Высокий порог входа в Otel Collector

- **Нужно:**
  - время на изучение синтаксиса YAML-конфигов OTel, чтобы избежать «молчаливой» потери данных при неверной настройке цепочки обработки.
- **Так как:**
  - OTel Collector (pipelines, processors, exporters) значительно сложнее, чем настройка классических агентов (Promtail/Filebeat)

### ⚙️ Система мониторинга тоже требует мониторинга

- **Нужно:**
  - Обязательное включение внутренних метрик самого коллектора (internal<sub>metrics</sub>) для контроля его здоровья.
- **Так как:**
  - Может быть трудно понять, на каком этапе «застряли» логи или метрики

### ⚠️ Риск ломающих изменений в новых версиях

- **Когда:**
  - При обновлении компонентов OpenTelemetry
- **Может:**
  - Сломаться парсинг логов или отображение метрик в Grafana
- **Так как:**
  - Стандарт OTel активно развивается, и форматы экспорта могут меняться между версиями
- **Решение:**
  - Фиксация версий образов коллектора и тестирование обновлений на стейджинге перед продом.

### ⚠️ Риск конкуренции за ресурсы прода и мониторинга

- **Когда:**
  - При высокой нагрузке, особенно при работе Otel в режиме Gateway
- **Может:**
  - произойти конкуренция за ресурсы между основным монолитом и системой наблюдаемости.
- **Так как:**
  - OTel Collector — это полноценное приложение, которое потребляет больше RAM, чем узкоспециализированный Filebeat.
- **Решение:**
  - Необходимо четко лимитировать ресурсы (CPU/Memory) для агента

### ⚠️ Риск раздувание метрик при высококардинальных данных

- **Когда:**
  - Например, user<sub>id</sub> сделан частью traceId метрики
- **Может:**
  - Prometheus может быстро исчерпать лимиты памяти
- **Так как:**
  - Micrometer начнет генерировать метрики с уникальными значениями user<sub>id</sub> в лейблах
- **Решение:**
  - Требуется строгий аудит кода и использование Processors в OTel Collector для удаления или агрегации высококардинальных данных до их попадания в хранилище.
